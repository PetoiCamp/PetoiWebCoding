Bittle X 仿真器与 main.html 集成

技术分析与协作需求说明 · 目标页面：bittle-x-sim.aperobotics.io

摘要：在 main.html 底部用 <iframe> 嵌入该仿真站，从当前 HTTP 响应头看通常可行；但父页面无法跨域自动填写仿真器内的 Serial 输入框或触发发送，除非仿真页面提供明确的 postMessage（或同类）集成接口。

1. 背景与目标

Petoi Web Coding（main.html）通过 Web Serial / WebSocket 向真实机器人下发指令。希望在同一页面底部嵌入 Bittle X 浏览器仿真，并在理想情况下将同一条逻辑上的串口命令同步到仿真器的 Serial 输入，用于无硬件预览或教学演示。

2. iframe 嵌入可行性

对仿真站首页响应头检查（示例时间点）中，未发现常见的 X-Frame-Options: DENY/SAMEORIGIN，也未发现限制嵌入的 Content-Security-Policy: frame-ancestors。因此在默认浏览器策略下，一般允许从 Petoi 页面以 iframe 加载该 URL。

注意 第三方站点随时可能收紧策略；若将来增加 frame-ancestors，嵌入将失效，需改方案（如新窗口打开或同源自托管）。

3. 为何不能直接操作 Serial 输入框

main.html 与 aperobotics.io 为不同源。浏览器同源策略禁止父页脚本读取或修改 iframe 内 DOM（包括给 “serial monitor input…” 赋值、模拟点击 “Send”）。

对仿真站点 bundle.js（体积约 5MB）中与 postMessage / message 相关代码的核查表明：命中内容主要来自打包的运行时/编辑器等依赖，不能视为已向父页面开放的 Serial 注入 API。

结论 在无官方集成约定前，不可行从 main.html 直连“写输入框 + 发送”。

4. 推荐协作需求（给仿真维护方）

建议在仿真页面顶层增加 window.addEventListener('message', …)，仅接受可信 origin（例如 https://code.petoi.com、开发用 http://localhost:*），并将消息转发到现有 Serial 发送管线（与用户在输入框按 “Send” 等价）。

建议消息格式（示例，可协商）

父页向 iframe：

iframe.contentWindow.postMessage(
  {
    source: "petoi-web-coding",
    type: "serial-send",
    text: "您的命令字符串或单行"
  },
  "https://bittle-x-sim.aperobotics.io"
);

可选：约定 type: "serial-send-binary" 配合 bytes 数组，以便与 Web Serial 字节路径对齐；或使用单一字符串协议以简化实现。

仿真页回传（可选）

如需确认或错误提示，可通过 event.source.postMessage({ … }, event.origin) 向父页回执，便于在 IDE 内打日志。

5. 实现路径对比

方案 说明
官方 postMessage API 父页在发往真实硬件的同时镜像一条消息进 iframe；安全、可维护。推荐
同源自托管仿真构建 技术上可同时源访问 DOM，但脆弱（对方升级易碎），且许可与构建成本需评估。
仅并排标签页 无工程集成，依赖人工复制命令。

6. 与现有 main.html 的关系

当前 main.html 中串口/Wi‑Fi 发送逻辑（例如 serialRequest、writer.write、WebSocket 客户端）与仿真器内部 Serial 为两套通道。集成时应在现有发送路径上增加可开关的镜像调用（避免无 iframe 或未连接仿真时报错），并在收到维护方最终协议后再定稿字段名与安全名单。

本文档为技术说明与需求草案，随对方 API 定稿可再收紧示例代码与 origin 白名单。本地预览：在仓库根目录执行 npm start 后访问 /bittle-sim-integration.html。
